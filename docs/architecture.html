    What actually crosses the wire

    PayloadWritten byContents
    scene_config Set Design Agent Room dimensions, props, lighting, camera placement and its move. One typed object. The browser preview and the USD builder read the same schema, so the preview can never drift from what gets simulated.
    set.usda USD Builder A real OpenUSD stage: geometry with collision meshes, an off-set marker on anything outside the built space, and a camera whose move is baked as time samples.
    result.json GPU host Rendered frame paths, the captured video, and machine-readable findings: coverage flags, physics flags, and camera-collision flags with the exact frame, frustum corner and prim involved.
    fix report Validation Agent A plain-language summary, the issues found, what fixing each one buys the shot, and a list of typed fixes the backend knows how to apply: change_lens, reposition_camera, add_wild_wall.

    Components

    Browser

    Web app

    The whole director-facing surface. Chat, live 3D preview and the review panel sit side by side so a change and its consequence are visible at once.

    • React app, single page
    • Three.js renders scene_config directly: walls, props, dolly path, camera frustum
    • Review panel plays the simulation video against the flagged frames

    Service

    Backend orchestrator

    The only component that talks to everything else. Holds the thread, owns the scene, and decides when to call a model versus the GPU host.

    • FastAPI: /chat, /generate-usd, /render, /propose-fix
    • Authors USD with pxr.Usd rather than emitting text
    • Keys every stage, render and report to one scene_id

    Reasoning

    Set Design Agent

    Turns a sentence into a scene graph. Asks for what is missing first; only emits structure once the brief is complete.

    • Cheap fast model for clarifying turns, stronger model for extraction
    • Output is the typed scene_config, never free text the renderer has to parse

    GPU host

    Omniverse Kit runtime

    One USD stage serves the scene graph, the physics and the renderer. Nothing is exported between tools, so the thing being validated is the thing being shown.

    • PhysX casts four frustum-corner rays per sampled frame against real collision meshes
    • Flags rays that reach past the built set, and rig geometry the camera would hit
    • RTX renders the move; frames captured to video

    Reasoning

    Validation Agent

    Reads the run and writes the report. Constrained to fixes the simulator can actually re-check, so a proposed fix is a testable claim rather than a plausible sentence.

    • Input: flags plus the scene they came from
    • Output: summary, issues, benefits, typed fixes
    • Read-only: nothing is applied until the director says so

    Loop

    Fix and re-verify

    The part that makes the tool trustworthy: a fix is applied, the stage is rebuilt, and the identical checks run again so the before / after count is real.

    • Fixes mutate scene_config, then USD is regenerated, never patched
    • A fix that fails to clear its flag is reported unresolved, not dropped

    Design intent. Two boundaries carry the weight of this architecture. The first is the schema boundary: scene_config is the only description of the set, so the preview, the USD stage and the validator can never disagree about what is being built. The second is the process boundary at the GPU host: reasoning happens outside it, physics happens inside it, and only files cross.
